# 词库丰富方案（v1 讨论稿）

> 目标：回答「数据不够，怎么丰富」，并给出可执行、可验收、有停止条件的机制。
> 所有数字均为本机实测，脚本可重跑复现。

---

## 0. 一句话结论

把「拍脑袋想词条」换成 **任务链生成 + 脚本加工 + 双轨并集**，
并明确 **目标不是 2500 常用字，而是约 1300–1500 字**（覆盖"生活自治"所需即可）。

---

## 1. 现状诊断：为什么现在扩展不动

| 现象 | 根因 |
|---|---|
| 36 个词条，无法扩展 | 没有**生成机制** —— 词条是"看标识牌想出来的"，想完就没了 |
| 不知道"够了没" | 没有**验收指标** —— 覆盖率算的是字，缺口却全是虚词 |
| 两份数据手工同步 | `StudyData.kt` 与 `prototype/index.html` 各写一份，必然漂移 |

上一轮已实测：现有 36 词 = 87 个去重汉字 = 2500 常用字的 **3.44%**；
但缺口前 120 位是 `的 是 不 了 在 人 有 我 他 这 个 们 中…` —— **全是语法虚词**。
说明「补词条 → 追覆盖率」这条路方向是错的：这些字根本不出现在标牌上。

---

## 2. 机制：从「生活任务链」展开

**核心转变：不从字出发，也不从词出发，从「老人要办成的事」出发。**

因为目标不是"覆盖多少字"，而是"老人能不能独立办成事"。
前者是字集合，后者是任务完成率 —— 骨架必须是任务。

### 输入规范（人只写这五列）

| 列 | 说明 | 示例 |
|---|---|---|
| 生活域 | 大类 | 就医 / 购物 / 出行 / 金融 / 政务 … |
| 任务 | 一件具体要办成的事 | 社区医院开药 |
| 步骤 | 任务链上的环节，按真实顺序 | 进院 → 挂号 → 候诊 → 就诊 → 缴费 → 取药 → 离院 |
| 词条 | 该步骤里真实会看到/听到的 2–6 字 | 挂号处、医保卡、忌辛辣 |
| 提示语 | 一句大白话，老人能懂 | 刷卡看病能少花钱 |

**人不写拼音、不数数、不判重。** 这些全部由脚本产出。

### 脚本产出（`expand.py`，可重跑）

逐字拼音（多音字按词组上下文取音）、字频名次、字集、新增字检测、
覆盖率、跨任务边际衰减、重复词条检测。

### 实测结果（已跑通，2 个任务链）

| 生活域 | 任务 | 步骤 | 词条 | 去重字 | 净新增字 | 新字率 |
|---|---|---|---|---|---|---|
| 就医 | 社区医院开药 | 7 | 36 | 76 | **47** | 62% |
| 购物 | 超市买菜 | 7 | 35 | 63 | **34** | 54% |
| | **合计** | | **71** | **125** | **81** | |

- **超出 3500 常用字表的字：0 个** —— 场景用字完全落在常用字表内
- 落在 2500 常用字内：98.8%
- 平均每任务产出约 **70 个去重字**，约 **35 个净新增字**

**三个被数据纠正的先验：**

1. ❌ 我原以为"场景字多为中低频" —— **错**。81 个新增字里 44 个在字频前 500 名。
   场景用字以高频字为主，说明「常用字表」与「生活场景」并不冲突。
2. ❌ 我原来假设跨任务新增字率会掉到 55% —— **错，实测 62% → 54%，跨生活域几乎不衰减**。
   真正会衰减的是同一生活域内的第 2、3、4 个任务（反复出现同一批字）。
3. ✅ "图片只是辅助" —— 数据支持。词条的价值在于产出**字**，图片不参与识字本身。

## 3. 双轨制：为什么纯任务链会到顶

任务链有一个**结构性天花板**：它永远产不出虚词。

实测：字频前 200 名里，任务链只覆盖了 **35 个（17.5%）**，**盲区 165 个**：

```
的 是 不 了 在 人 我 他 这 个 们 中 上 大 为 和 国 地 到 以
说 要 就 可 也 你 对 能 而 子 那 得 于 着 自 之 作 里 道 行
所 然 家 种 事 成 方 多 经 么 去 学 如 都 同 当 没 动 面 起
看 定 天 分 还 进 好 部 其 些 主 样 理 心 她 本 开 但 因 只
```

每个区间都测一遍：

| 字频区间 | 字数 | 任务链覆盖 | 覆盖率 | 盲区 |
|---|---|---|---|---|
| 1–200 | 200 | 35 | 17.5% | 165 |
| 201–500 | 300 | 38 | 12.7% | 262 |
| 501–1000 | 500 | 18 | 3.6% | 482 |
| 1001–1500 | 500 | 19 | 3.8% | 481 |
| 1501–2500 | 1000 | 11 | 1.1% | 989 |

**结论：任务链到约 900–1000 字就到顶了。剩下的必须由第二轨补。**

### 两条轨的分工

| | 轨 A · 场景轨 | 轨 B · 基础轨 |
|---|---|---|
| 来源 | 生活任务链（人写五列） | 3500 常用字表按字频 top-down |
| 产出什么字 | 标牌字：挂 / 缴 / 签 / 诊 / 忌 / 罩 | 语法字：的 / 是 / 了 / 我 / 你 / 和 |
| 配图 | 具象字配图（辅助） | 不配图，改高频搭配：我的 / 好的 / 还是 |
| 卡片形态 | 单字大字号 + 组词 + 场景底图 | 单字大字号 + 高频搭配 |
| 大约规模 | ~1300 词 / ~930 字 | 补前 500 名盲区 427 字 → 累计 ~1350 字 |

两轨在**「字」这一层合并** —— 同一个 `Character` 实体，用 `source` 字段标记来源，
调度器不区分，复习卡统一出单字。

## 4. 数据模型演进

`Term`（单一实体）→ `Character` + `Word`（两实体），`Word` 降级为载体。

```
Character {
  c          字
  p          拼音          ← 脚本生成
  radical    部首          ← 记忆钩子（数据源待验证）
  strokes    笔画数        ← 笔顺动画需要（hanzi-writer）
  freqRank   字频名次      ← 排序用，脚本生成
  sceneValue 场景价值      ← 排序用，规则 + 人工校
  source     scene | freq  ← 标记来自哪条轨
  contexts[] 语境列表      ← 必填，1–3 条真实词组/搭配
}

Word {                     ← 从「学习单元」降级为「语境载体」
  text, chars[], tip, domain, task, step
}

TaskChain {                ← 新增：任务链，语境的来源
  domain, task, steps[], words[]
}
```

> ⚠️ 「挂」字频排第 **1231** 名。纯按字频推教学，结果是
> "老人认全了『的、是、不、了』，站在挂号处还是懵"。
> 所以排序必须**双维度**：`sceneValue` 权重高于 `freqRank`。

## 5. 工作流与分工

| 环节 | 谁做 | 产出 |
|---|---|---|
| 枚举生活域 / 任务 / 步骤 | **人**（QYJ，需生活经验） | TSV 五列 |
| 写词条 + 提示语 | **人** | 同上 |
| 注音、字频、字集、去重 | 脚本 | `wordbank.json` |
| 覆盖率 & 盲区验收 | 脚本 | 报告 |
| 生成两端代码 | 脚本 | `StudyData.kt` + `prototype` 数据段 |
| 部首 / 笔画 / 场景价值分 | 脚本 + **人工抽查** | 标注字段 |
| 卡片形态验证 | 人 | 样张确认 |

**关键收益：单一数据源（TSV）→ 脚本生成两端。** 手工同步两份数据的问题从根上消失。

## 6. 词条从哪来、错在哪、谁校对

**结论：词条是"写"出来的，脚本不生成词条。生成与加工必须严格分开。**

| 环节 | 谁做 | 性质 |
|---|---|---|
| 枚举任务 / 步骤 / 词条 / 提示语 | 人 或 模型 | **内容生成，不可验证，必须校对** |
| 拼音 / 字频 / 字集 / 去重 / 覆盖率 | 脚本 | **确定性计算，可复现，不需要校对** |

两条硬规则：

1. **拼音一个字都不能让模型写** —— 几百条手写必错，必须由 pypinyin 按词组上下文算
2. **字频、字集、去重必须查表/脚本算** —— 这两类出了错能复现、能修，不该混进"人工校对"的范畴

### 模型生成的真实错误率（拿我这批 71 条自查）

我对自己的输出做了逐条审计：

| 错误类型 | 例子 | 数量 |
|---|---|---|
| A 硬幻觉（编造不存在的标识） | 「下次再来」—— 不是任何牌子上的字 | 1 |
| B 说法不地道 | 「请等候」（牌子写"请稍候"）、「调料」（超市标"调味品"）、「计价」（标"称重处"）、「环保袋」「忌辛辣」「导诊台」「请勿喧哗」 | 7 |
| C 性质混杂（不是标识，是口语/症状） | 「三楼」「塑料袋」「头晕」「咳嗽」 | 4 |
| D 地域/机构差异 | 「老年科」（社区医院不一定设） | 1 |

**合计约 13 条 / 71 条 ≈ 18% 需要人工修一遍，但硬幻觉只有 1 条（1.4%）。**

这个分布可接受，理由有三：

1. 错误集中在**"说法地道性"**，不是"这东西存不存在" —— 校对成本低，**不需要医学/行业专家**
2. 全部可被一个常去医院/超市的普通人检出，36 条约 20 分钟
3. **换我再写一遍，错误类型完全一样** —— 这是生成方式的结构性特征，**不是提高生成质量能解决的**，所以校对环节必须固化进流程

### 三条来源路线，可靠性递增

| 路线 | 做法 | 可靠性 | 成本 |
|---|---|---|---|
| ① 模型生成 | 我按任务链写，人审 | 中（约 18% 待修） | 低 |
| ② 实地采集（**推荐**） | 你或家人去社区医院/超市拍一圈照片，我从照片里提取标识 | **高**（真实存在，不会幻觉） | 一次走一圈 |
| ③ 公开语料 | 政务办事指南、公开标识图集 | 中高 | 需整理 |

**建议 ① + ② 组合**：先用模型生成把任务链骨架和步骤建起来（快），
再让一次实地拍摄把 `sign` 类词条替换成实拍核对过的（准）。
拍照这条路成本极低 —— 一个熟悉的人带手机走一圈，就能覆盖一整条任务链的全部真实标识，
而且顺手能补上"我编不出来"的那些牌子。

### 写进验收的硬性规则

1. 拼音、字频、部首、笔画一律脚本生成，**不接受手写**
2. 每条词条标 `source`：`sign`（标牌）/ `med`（药盒说明书）/ `oral`（口头医嘱）/ `form`（表单字段）
3. `source = sign` 的词条**上线前必须有实拍或人工确认**；`oral` 类不参与"标识识别"验收
4. C 类（口语/症状）单独成组，**不与标识混排在同一步骤里** —— 它们要的是"会听会说"，不是"看得懂"

## 7. 量级推算与停止条件

模型：新字率从实测 62% 起步，等比趋近饱和下限 30%（按第 2 个实测点反推衰减因子 0.75），
每任务平均产出 70 个去重字。

按 **9 个生活域 × 每域 4 个任务 = 36 个任务** 推算：

| 推算项 | 数值 |
|---|---|
| 总词条数 | 约 1278 |
| 累计覆盖不重复字 | 约 927 |
| 对应 2500 常用字覆盖 | 约 37% |

敏感性（饱和下限取值）：

| 饱和下限 | 累计覆盖字 | 2500 覆盖 |
|---|---|---|
| 25% | 约 832 | 约 33% |
| 30% | 约 927 | 约 37% |
| 35% | 约 1026 | 约 41% |
| 45% | 约 1238 | 约 50% |

**停止条件：** 某任务新字率 < 20% 且未引入新步骤类型时，该任务边际价值已低，停止扩张。

**加上轨 B 补前 500 名盲区 427 字 → 累计约 1350 字（2500 的 54%）。**
这就是"生活自治"目标的现实终点。追 2500 需要约 3500+ 词条且抽象字占比极高，性价比很差。

## 8. 分期路线

| 阶段 | 范围 | 产出 | 验收 |
|---|---|---|---|
| **P0 跑通** | 4 个任务链（就医 ×2、购物 ×2） | ~140 词 / ~200 字 + 卡片样张 | 卡片形态确认、调度可跑 |
| **P1 铺开** | 9 域 × 4 任务 = 36 条任务链 | ~1300 词 / ~930 字 | 覆盖率 ≥ 35%、无字超出 3500 |
| **P2 补齐** | 轨 B 高频盲区 427 字 + 部首/笔顺标注 | 累计 ~1350 字 | 前 500 名盲区 ≤ 5% |

每阶段都产出可运行的两端数据，不会出现"做一半不能用"。

## 9. 与现有 prd 的冲突（需回 Plan 修订）

prd v2 第 3 条原文：

> 以生活中真实出现的**组合**为单元（如"地铁站"一起学，**不拆成地/铁/站三课**）

字本位与这条**正面冲突**。同时失效的还有：

1. 数据模型从 `Term` 一实体变为 `Character` + `Word` + `TaskChain` 三实体
2. 词条量级从 36 → 1000+，prd 里"36 词量级不上 Room"的前提失效
3. 数据源从硬编码 Kt/HTML 迁到 TSV + 构建期生成脚本
4. 需要 `assets`（笔顺动画数据、可选配图）

按 Trellis 规矩，这属于 prd 缺陷，**应回 Plan 阶段正式修订文档，不能默默改代码**。
