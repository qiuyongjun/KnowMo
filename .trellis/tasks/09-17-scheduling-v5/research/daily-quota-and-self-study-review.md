## 一、设想 1：每天分配 10 个或 n 个词（含新词或复习词），后期可设置

### 1.1 当前实现逻辑（逐段）

| 步骤 | 位置 | 做什么 |
|---|---|---|
| 装载 | `AppRoot.LaunchedEffect(channel)` | `repo.ensureQueue("rec")`；date 相符就复用（当日冻结），否则重建 |
| 取范围 | `scopeIds("rec")` | 全部 368 词（毕业分区不排除） |
| 已学词排序 | `buildQueue` | `learned = scope.filter { termStates[it] != null }`，双键：`lapses` 降序 → `dueTime` 升序 |
| 到期筛选 | 同上 | `due = learned.filter { isDue(it) }`（`lastSeen + days ≤ 今天`） |
| 新词 | 同上 | `news = scope.filter { termStates[it] == null }.shuffled()` |
| **配额** | 同上 | `due.size >= 20` → `due.take(15)`（清债模式，**不补新词**）；否则 `(due + news).take(10)` |
| 摊成卡 | 同上 | **每词一张卡**，`mode = NEW`（无 TermState）或 `REVIEW` |

### 1.2 逐要素核对

| 设想要素 | 实现 | 判定 |
|---|---|---|
| 每天分配固定数量 | `DAILY_POOL_QUOTA = 10`；`(due + news).take(10)` | ✅ 满足（n = 10） |
| 含新词**或**复习词 | 到期复核优先，新词补足差额 | ✅ 满足 |
| n 后期可设置 | 硬编码 `const val`，无设置入口、无持久化字段 | ⏳ 已声明为后期 |
| —— | 清债日 due ≥ 20 时自动变成 **15 个词** | ⚠️ 见 1.3-C |
| —— | 1 个词 = 3–4 张卡 | ⚠️ 见 1.3-A |

### 1.3 四处出入（A/B 是最重要的两条）

**A.「词」与「卡」是 3–4 倍关系，且这是用户唯一能感知的单位**

- 复习词：需连对 3 次才移出 → `answer` 未满 3 就 `appendReviewCard` → **3 张卡/词**
- 新词：1 张教读卡 + 3 张考核卡 = **4 张卡/词**
- 于是：配额 10 全复习 = **30 张**；配额 10 全新词 = **40 张**；清债日 15 全复习 = **45 张**

用户设想的「分配 10 个词」，落到手上是 30–45 张卡。若将来把 n 做成设置项，直接暴露「词数」会误导——高龄用户在设置里看到「20」会预期 20 次滑动，实际是 60–80 张。

**B. n 有一个隐式天花板：可递送词数 ≈ 30n**

间隔封顶 30 → 已学词全部到顶后，每日到期量 ≈ 已学词数 / 30。配额 n 时，`due` 吃满配额即 `news` 为 0：

```
可递送词数上限 ≈ 30 × n
n = 10 → 300 词        词库 368 → 68 词（18%）永远进不了推荐频道
n = 13 → 390 词 ≥ 368  全库可达
```

这条直接决定「n 可设置」这个功能的意义：**它同时是当前缺陷的解法**。修 B 不必动阶梯，只需让 n 能调到 13 以上。（推导与模拟数据见 `learning-mechanism-review.md` 与 `mechanism-sim-report.txt`。）

**C. 清债模式的常量是按 n = 10 写死的**

```kotlin
DEBT_THRESHOLD = 20   // due ≥ 20 触发
DEBT_QUOTA     = 15   // 扩到 15 词
```

现在 15 > 10，所以它是「扩容」。n 一旦可设置：

- n = 12 → 清债日给 15 词（仍算扩容，勉强合理）
- **n = 20 → 清债日给 15 词，比平常还少**（扩容变成了缩水）

所以 n 可设置之前，必须先决定这两个常量相对 n 的定义（例如 `max(n, 15)`，或 `n * 1.5`）。这是「后期改成可设置」真正的技术前提，不是加一个 UI 开关。

**D. 分区也是新词入口，且是一条会「埋债」的入口**

分区 `pool = learned + news`（R9：不做到期筛选，全量入队），所以**分区会教新词、会写 `TermState`**。刷完一个全新的「医院」（32 词）当天就多出 32 个已学词，**次日全部到期**（`days = 1`）。这与设想 1 的「每日任务分配 n 个词」在语义上是两个入口，且分区那条不受 n 约束、用户看不见、明天却要拿每日任务的配额来还。

**E.「分配」在界面上不可见**

契约第 6 条明确「不展示第 x/y 张进度条，进度由完成卡和语音表达」。用户全程不知道今天有几个词，只有完成卡上说「今天学完了 N 个词」。如果「分配 n 个词」是要让用户**感知到**的任务量，目前只有结果、没有过程。

## 二、设想 2：学完每日任务可自主学习，无限制、不需要选择是否认识，可选分区也可在推荐中随机给词

### 2.1 当前实现逻辑

**推荐频道的随机刷（= 温故流）**

```
完成卡出现（pendingTaskCount() == 0，仅 rec）
  → 翻页 effect 里 doneIdx >= 0 且 idx >= doneIdx - 1
  → appendFreePages(2)
  → freePool = repo.freePoolIds("rec").mapNotNull(::termById)   // 洗牌；抽完重洗
  → Page.TermPage(t, CardMode.FREE, nextSeq(), qIndex = -1)     // -1 = 不落库
```

**分区（自主练习）**

```
buildQueue(分区) = learned + news（全量，不做到期筛选）
  → 无完成卡（syncDonePage 直接 return）
  → 无前向拦截（blockingIndex 直接 return -1）
  → 滑完停住 + 最后一张 footerHint / SCENE_TAIL_SPEECH
  → 断点 = q.position（上次那一页）
  → 卡形态仍是 NEW / REVIEW，同样有 √/×，同样走 answer() → 写间隔层、写战果
```

**温故卡（FREE）的界面形态（`TermCard.kt`）**

- `isExam = mode != CardMode.NEW` → **FREE 是考试态**：先只出词，不出拼音与提示
- 未作答点卡片 → 只说「再想一想，想起来了吗？」（防泄题）
- 底部两个大按钮 `× 忘了` / `√ 认识` + 引导「👆 想不起来？点下面的按钮」+「👀 想看答案」
- 作答 → `markKnown` / `markForgot` → **写间隔层**（可提前升级 / 打回 days=1、lapses+1）+ 不追加队列 + 自动前进

### 2.2 逐要素核对

| 设想要素 | 实现 | 判定 |
|---|---|---|
| 学完每日任务才能自主学习 | 推荐频道：`doneIdx >= 0` 才追加 free 页，未做完没有 | ✅（**仅推荐频道内部**成立） |
| （同上） | 分区**随时可进**，不设任何门槛 | ⚠️ 见 2.3-F |
| 自主学习没有限制 | 推荐：抽完重洗、无限流 | ✅ |
| （同上） | 分区：**滑完停住**（上一轮的决定） | ⚠️ 见 2.3-G |
| 可选择分区 | `ChannelBar` 12 个分区常驻可点 | ✅ |
| 推荐中由软件随机给词 | `freePoolIds("rec")` 洗牌；只含**已学过**的词 | ✅ |
| **不需要选择是否认识** | FREE 卡有 √/× 大按钮、考试态、作答写间隔层 | ❌ 见 2.3-H |

### 2.3 三处出入

**F.「学完才能自主」不是硬约束——分区是并行的第二入口**

分区随时可进、无完成卡、还能教新词。因此「先完成任务、再自主学习」只描述得了推荐频道内部的顺序，描述不了 App 的整体结构。这可能是你想要的（老人随时能玩），但**它不是当前实现的性质，而是缺省结果**——如果这是想要的，应该主动定成契约；如果不是，需要一道门槛。

**G. 分区「滑完停住」与「自主学习没有限制」有张力**

上一轮你选的是「滑完停住 + 轻提示」，本轮说「自主学习没有限制」。分区队列 = 该区全部词，滑到最后一张就停。若「没有限制」是硬要求，分区应改成**滑完继续追加该区已学词**（无限流）——但那样队尾轻提示就没有出现时机了，两者需要二选一。

（推荐频道的随机刷不受这条影响，它本来就是无限流。）

**H.「不需要让用户选择是否认识」是唯一的硬出入，且牵动三条已确认决策**

这是本轮最重的一条。当前温故卡与分区卡都是**考试形态**，都要求（或至少强烈引导）自评 √/×。三种落法：

**(a) 纯浏览卡** — 温故与分区都改成「新学卡形态」：词 + 拼音 + 提示全展开、无按钮、点卡片重听、点单字看讲解。

- 收益：彻底不需要自评；消除「温故随手 √ 提前升级 / 随手 × 打回 1 天」这条不确定性（`learning-mechanism-review.md` 的 C 项）；单卡成本从 3–4 张降到 1 张。
- **代价 1（与已确认决策冲突）**：上一轮你定的是「温故如果忘了，需要重新学习」——它成立的前提正是有 × 可按。改成纯浏览后，机制**不知道用户在温故里忘掉了什么**，该词要等原到期日才会回到每日任务（间隔最长 30 天）。等于撤销上一轮的决定。
- **代价 2（连锁）**：**分区不能再教新词**。间隔层只在连击满 3 时写入（`markKnown`），不考核就永远写不出 `TermState` → 分区里的新词永远停在「新学」、每天重复教读。所以分区的 `news` 必须从 pool 里去掉，分区只出已学词。
- **代价 3**：完成卡战果口径要重定义。现在 `knownAnswers` / `forgotAnswers` 是「当日任何频道的作答次数」；只读后温故与分区不产生作答，x/y 实际只统计每日任务频道。
- **代价 4**：R8 的「作答后自动前进」对 FREE 卡失去触发点（没有作答事件）。

**(b) 保留作答但降权** — 默认展开答案，用户想反馈才点按钮。

- 兼容前两轮的全部决策，但「不需要选择是否认识」只做到一半：按钮还在，只是不挡路。

**(c) 只对分区纯浏览** — 分区改成只看不写，推荐频道的温故流保留作答。

- 与「分区 = 自主练习 / 温故 = 随便看看」的现有语义最贴，但不满足这句话的字面（你说的是「自主学习」，分区只是它的一种形式）。

### 2.4 一条结构性观察

设想 1 的「每日 n 个词配额」与设想 2 的「学完才能自主」，是同一个配额的两端。而**分区是唯一一个既不占用这个配额、又能学到新词、又能改写间隔层、又能计入战果的入口**——它是「每日任务」这个中心概念被稀释的全部来源。若采纳落法 (a)，分区自动收敛成「只看不写」的练习区，中心概念反而更干净。

`prototype/index.html` 的 `renderFeed()` 只做 `feed.innerHTML = buildQueue(state.channel).map(termCardHTML)`，**没有实现温故流**（无 free 页追加逻辑，`appendFreePages` 在原型里不存在）。因此设想 2 的「在推荐中由软件随机给词」这条契约，**原型里没有对应实现**。按项目约定（同一套交互契约两边各实现一份），真要动这条时，原型也要补。

## 五、这三个决定连锁推出的七个问题

**P1（最重要）「分区含全部词」+「纯浏览」= 分区里没学过的词，看多少遍都不会变成已学**

纯浏览卡不能作答 → 不调用 `markKnown` → 间隔层只在连击满 3 时写入 → **`TermState` 永远不产生** → 该词次日仍是「未学」，在分区里继续以未学身份出现。

所以分区的语义**必然**是：「该区所有词都能看，但**只有每日任务教过的才算学会**」。如果预期是「在分区里也能学会新词」，那分区对未学词就必须保留考核形态——与 D1 冲突，二者只能选一个。

配套约束：分区卡**不得**再调 `markSeen`（首次返回 true 时会 `appendReviewCard` 追加考核卡，直接破坏「纯浏览」）。

**P2 分区断点失去意义**

顺序随机后，「第 k 页」每次指向不同的词，`saveQueuePosition` 对分区不再有意义。要么每次进分区重新开始（不恢复位置），要么改成按**词 id** 恢复。

**P3 分区从「队列」变成「池」**

现在的分区是 `DailyQueue`（`queue` / `modes` / `answered` 三数组 + `position`，整体落库）。改成无限流随机后，结构上更接近推荐频道的 `freePool`：运行时抽取、抽完重洗、不落库。连带：

- `buildQueue` 的分区分支不再需要排序与 `modes`（全浏览卡，没有 NEW / REVIEW 之分）
- `ensureQueue(分区)` 的持久化、`markAnswered`、`saveQueuePosition` 对分区不再适用
- 推荐频道**不变**（仍需 `DailyQueue` 做当日冻结 + 断点 + 完成卡判定）
- 于是数据结构上要区分**队列型频道**（rec）与**池型频道**（分区）

**P4 「学习频次」只能从已有状态里只读地取**

纯浏览不写状态，所以加权随机的权重只能来自已有的 `TermState`（`lapses` / `days` / `lastSeen`）与 `DayState.counts`，**只读参与权重、不写回**。未学词没有 `TermState`，需要单独定义权重。

一个可用的形式：`w = 1 + 2×lapses + (距上次学习天数 ÷ 30)`，按权重轮盘抽取；未学词给固定权重。

**P5 完成卡战果口径自动收敛（好消息，几乎不用改代码）**

`knownAnswers` / `forgotAnswers` 只在 `answer()` 里 +1。温故与分区不再有作答入口 → 计数天然只剩每日任务频道。代码不动，只需把 prd 里「全局当日口径」改写为「每日任务频道口径」。

**P6 队尾轻提示与 R8 自动前进都要收窄**

- `SCENE_TAIL_HINT` / `SCENE_TAIL_SPEECH` / `isSceneTail` 全部删除（无限流之后没有「最后一张」）
- R8 的自动前进对 FREE 卡失去触发点（没有作答事件）；且**不应**给浏览卡做自动前进——用户还没看完就翻页。R8 收窄为「仅每日任务频道的 REVIEW 卡」
- 防泄题话术（`EXAM_TAP_HINT_SPEECH`）同样收窄到 REVIEW 卡：浏览卡不考，点一下就该直接念词

**P7 原型要补的东西变多了**

`prototype/index.html` 既没有温故流，分区也是「全量固定顺序」。本轮之后它需要：分区池型随机流 + 无限追加 + 纯浏览卡形态。原型与安卓的差距从「缺一条温故流」扩大到「缺整个池型频道模型」。

## 六、定案后的完整变更清单（实现层索引）

**StudyRepository.kt**
- `buildQueue` 的分区分支删除：分区不再生成 `DailyQueue`（池型频道没有队列，也没有 `modes` / `answered` / `position`）
- 新增分区池函数：`scenePoolIds(scene)` = 该区全部词（含未学），按 D5 的权重做加权洗牌
- 新增权重函数：`w = f(lapses, days, lastSeen)`，未学词取固定值
- `ensureQueue` / `saveQueuePosition` / `markAnswered` / `appendQueue` 对分区不再适用（推荐频道不变）
- 频道语义分型：`CHANNEL_DAILY` = 队列型，其余 = 池型

**AppRoot.kt**
- `appendFreePages` 从「仅完成卡之后」扩展到「分区随时」（池型频道复用同一套追加逻辑）
- `isSceneTail` / `SCENE_TAIL_HINT` / `SCENE_TAIL_SPEECH` 删除
- 分区不再有 `restoreTo`（D6：不恢复位置）

**TermCard.kt / Common.kt**

## 七、两个必须记下的产品风险（不是 bug，是这次改动的固有代价）

**风险 1：温故流与分区不再产生任何学习记录**

区间层现在只有一个写入来源：每日任务的 REVIEW 卡作答。好处是机制不再被随手点击污染；代价是**老人在分区里「看」了很久，机制认为他什么都没发生**——没有进度、没有战报、分区 🎓 毕业徽章也只能靠每日任务推进。如果老人指望「多练就能快点学完」，这个指望落空了。

**风险 2：学习效果完全押在每日任务的 n 个词上**

温故与分区退化为消遣之后，间隔层每天的输入量就是 n（现在 10）。这意味着 `learning-mechanism-review.md` 里那组杠杆（连击目标、新词保底、封顶、配额）从「可选优化」变成了「唯一的调节手段」——尤其 n 的隐式上限 30n（见 §1.3-B）会直接决定词库走得完还是走不完。

## 八、其余仍在开放的问题

1. **n 可设置的两个技术前提**：`DEBT_QUOTA`（15）/ `DEBT_THRESHOLD`（20）相对 n 的定义；n 上限（13 起才能覆盖 368 词）。
2. **「学完才能自主」是否要成为硬约束**：分区随时可进，不设门槛。
3. **浏览卡要不要显示任何进度暗示**：例如「这个区你已学过 12/32 个词」——纯浏览如果完全没有反馈，高龄用户可能失去「在进步」的感受。
